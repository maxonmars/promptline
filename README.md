# promptline

CLI на TypeScript для диалога с LLM через DeepSeek API прямо в терминале.

## Как это работает

DeepSeek предоставляет API, совместимый с форматом OpenAI. Поэтому используется официальный пакет `openai`, у которого достаточно подменить `baseURL` на `https://api.deepseek.com`.

История диалога хранится в памяти процесса и отправляется целиком с каждым вопросом — значит, чем длиннее разговор, тем дороже каждая следующая реплика. При выходе история теряется.

Формат ответа, его длина, условие завершения и способ рассуждения задаются флагами и переключаются прямо в диалоге. Системный промпт собирается заново на каждый запрос, поэтому смена режима действует со следующей же реплики.

## Запуск

Нужен Node.js 20 или новее.

```bash
# 1. Установить зависимости
npm install

# 2. Создать .env из шаблона и вписать свой ключ
cp .env.example .env

# 3. Запустить
npm run dev
```

Ключ можно получить на https://platform.deepseek.com/api_keys — для запросов нужен положительный баланс.

## Использование

Без аргументов запускается диалог: вопрос — ответ — снова вопрос. Модель видит всю предыдущую переписку, поэтому можно уточнять («а короче?», «приведи пример»). Выход — `/exit`, Ctrl+C или Ctrl+D.

По умолчанию никаких ограничений нет — свободный текст, как в обычном чате. Все ограничения из раздела ниже включаются явно: флагом `--strict` при запуске или командой `/strict` прямо в диалоге, `/raw` возвращает обратно.

```bash
npm run dev                 # свободный чат
npm run dev -- --strict     # тот же диалог, но со схемой и лимитами
```

С аргументом — один вопрос, один ответ, выход. Флаги идут после `--`, иначе npm заберёт их себе:

```bash
npm run dev -- "Объясни, что такое REST API, в трёх предложениях"
```

Полный список флагов — `npm run dev -- --help`.

## Контроль формата

Ответ модели по умолчанию свободный: то абзац, то список, то с преамбулой. Три рычага делают его предсказуемым. Каждый можно задать отдельно, а `--strict` включает все разом: `json`, 60 слов, стоп-секвенция.

**Формат** — `--format=json|md|yaml|text`. Все три структурных формата описывают один контракт: `summary` плюс список `items` с полями `order`, `name`, `weight`. Для `json` дополнительно передаётся `response_format: { type: "json_object" }`, что делает валидность гарантией API, а не просьбой в промпте. Ответ проверяется локально, результат печатается строкой `формат ✓` или `формат ✗` с причиной.

**Длина** — `--max-words=N` кладёт инструкцию в промпт, `--max-tokens=N` ставит жёсткую крышку на стороне API. Это разные вещи: инструкцию модель трактует, крышка обрывает генерацию на полуслове и выставляет `finish_reason: length`.

**Завершение** — `--stop=SEQ` передаёт стоп-секвенцию в API и одновременно просит модель закончить ею ответ. Сам маркер в вывод не попадает: API отрезает его вместе с остатком.

```bash
# сравнить один и тот же запрос без ограничений и с ними
# (правую колонку --compare берёт из --strict, отдельно указывать не нужно)
npm run dev -- --compare "Дай рецепт салата цезарь"

# все ограничения разом
npm run dev -- --strict "Дай рецепт борща"

# проверить, что формат не плавает от запуска к запуску
npm run dev -- --repeat=3 --format=json "Дай рецепт борща"
```

Внутри диалога те же переключатели доступны командами: `/format`, `/strategy`, `/len`, `/tokens`, `/stop`, `/temp`, `/thinking`, `/raw`, `/strict`, `/limits`, `/help`, `/exit`.

## Способы рассуждения

Формат отвечает на вопрос «как оформить ответ», способ рассуждения — «как думать». Это вторая ось,
и с форматом она не сочетается: схема `summary`/`items` вытеснила бы разбор, поэтому сочетание
отклоняется на разборе аргументов, а не молча портит ответ.

| `--strategy` | что делает |
| --- | --- |
| `direct` | прямой ответ, к промпту ничего не добавляется (по умолчанию) |
| `steps` | «решай пошагово»: пересказ условия, проверка на подвох, нумерованные шаги |
| `meta` | два вызова: модель сначала сочиняет промпт для задачи, затем решает по нему |
| `experts` | аналитик, инженер и критик разбирают задачу под своими именами |
| `all` | прогнать все четыре на одном вопросе и сравнить |

У `meta` вызова два, и это видно в метриках: токены считаются за оба. Сгенерированный промпт
уходит системным блоком, а сама задача остаётся пользовательским сообщением — иначе промпт вида
«проанализируй приведённую задачу» оставил бы второй вызов без условия. В историю диалога попадает
исходный вопрос, не промпт.

**Точность** — `--expect="1/2|50%"` задаёт верный ответ, варианты через `|`. Промпт при этом требует
закончить строкой `FINAL: <ответ>`, и сверяется только она, причём целиком, а не подстрокой. Обе
строгости нужны: у пошагового разбора верное значение встречается в промежуточных прикидках при
неверном итоге, а «не Даша» содержит «Даша» и по подстроке засчиталось бы как верный ответ. Крайняя
пунктуация и регистр не мешают — «Даша.» и «Даша» считаются одним ответом.

Требование строки добавляется всем способам одинаково, включая `direct`, — иначе сравнение было бы
нечестным. Если строки `FINAL` в ответе нет, прогон считается неизмеренным, а не промахом: в
знаменатель доли попаданий он не входит и учитывается отдельной строкой под таблицей. В интерактивном
диалоге `--expect` не действует вовсе, о чём CLI предупреждает при запуске.

```bash
# сравнить четыре способа на одной задаче
npm run dev -- --strategy=all --expect="Даша" "<условие задачи>"

# пять прогонов каждым способом: доля попаданий вместо единичного впечатления
npm run dev -- --strategy=all --repeat=5 --expect="Даша" "<условие задачи>"
```

Способы идут последовательно, а не параллельно: одновременные вызовы делят общий rate limit, и
колонка времени перестала бы что-либо значить. Сбой одного способа печатается строкой и не роняет
результаты остальных.

```
═══ ИТОГО ══════════════════════════════════════════

способ                  попаданий  токенов   время
прямой ответ                  1/5      849   3.9 с
пошаговое рассуждение         4/5     5559  29.6 с
промпт от самой модели        2/5     5944  25.5 с
группа экспертов              5/5     5479  30.8 с
```

Разбор одной задачи всеми четырьмя способами, с ответами и выводами, —
в [docs/reasoning-strategies.md](docs/reasoning-strategies.md). Коротко: при включённом thinking mode способ
не влияет на точность вовсе, только на цену, потому что модель рассуждает и без просьбы.

## Температура

`--temperature=N` ничего не даёт сама по себе: у reasoning-моделей DeepSeek с включённым thinking mode (а он включён по умолчанию) API её принимает, но игнорирует. Чтобы температура реально влияла на разброс ответов, нужно явно выключить thinking: `--thinking=off`. Без этого CLI после каждого ответа с рассуждением подсказывает добавить флаг.

`--temperature=all` прогоняет один вопрос на 0, 0.7 и 1.2 и сводит результат в таблицу. Кроме попаданий и цены она считает разнообразие — сколько разных ответов пришло из N прогонов. Разные ответы считаются по значению строки `FINAL:`, поэтому контракт на эту строку включается и без `--expect`: свободные абзацы дословно не совпадают никогда, и уникальность вышла бы N/N на любой температуре.

```bash
# temperature ничего не даёт: thinking mode включён по умолчанию
npm run dev -- --temperature=1 "Назови одно животное"

# temperature реально работает — разные ответы от запуска к запуску
npm run dev -- --thinking=off --temperature=2 --format=text "Назови одно животное"

# три температуры на одном вопросе, по пять прогонов на каждую
npm run dev -- --thinking=off --temperature=all --repeat=5 "Придумай название для кофейни"
```

Температуры идут последовательно, ответы одной настройки печатаются подряд — иначе разброс не читается глазами. С `--compare` и `--strategy=all` флаг не сочетается: оси перемножились бы. При включённом thinking mode прогон не отклоняется, а предупреждает — колонки, которые не расходятся, и есть доказательство, что параметр игнорируется.

```
═══ ИТОГО ══════════════════════════════════════════

температура  уникальных  попаданий  токенов   время
0                  1/10       0/10     1690   7.9 с
0.7                5/10       4/10     2203  10.7 с
1.2                4/10       5/10    10656  70.3 с
```

Разбор с ответами и выводами — в [docs/temperature.md](docs/temperature.md). Коротко: на `0` модель повторяет один и тот же ответ десять раз подряд, и если он неверен — неверны все десять; попадания на `0.7` и `1.2` приходят не от «сообразительности», а от того, что случайный первый токен иногда запускает разбор вместо голого ответа.

## Особенности reasoning-моделей

`deepseek-v4-flash` сначала пишет рассуждение в отдельное поле `reasoning_content`, и только потом ответ. Из этого следуют три неочевидные вещи.

`max_tokens` покрывает рассуждение вместе с ответом, а длина рассуждения непредсказуема: на одном и том же вопросе она гуляет от 200 до 2000+ токенов. Низкая крышка приводит не к обрезанному ответу, а к пустому — весь лимит уходит на рассуждение. Поэтому `--max-tokens` по умолчанию не ставится: длину задаёт `--max-words`, а крышка остаётся явным флагом. Пустой ответ CLI объясняет отдельной строкой, а не печатает молча.

Стоп-секвенция сверяется и с текстом рассуждения. Если модель по дороге упомянет сам маркер («надо закончить на `<<<END>>>`»), генерация оборвётся до ответа. Случается редко, но CLI распознаёт и этот случай.

При `--format=json` стоп-секвенция не передаётся вовсе: `response_format` уже гарантирует закрытый объект, а маркер после него сломал бы разбор.

`temperature` у этих моделей ничего не решает: thinking mode включён по умолчанию, а [в этом режиме DeepSeek игнорирует `temperature`, `top_p`, `presence_penalty` и `frequency_penalty`](https://api-docs.deepseek.com/guides/thinking_mode/) — принимает параметр без ошибки, но не применяет. Поэтому `--temperature` по умолчанию не ставится, а при явном флаге CLI предупреждает, если в ответе всё же было рассуждение, и подсказывает добавить `--thinking=off` — единственный способ сделать температуру рабочей.

## Модели

| Модель | Когда использовать |
| --- | --- |
| `deepseek-v4-flash` | по умолчанию, быстрая и дешёвая |
| `deepseek-v4-pro` | сложные задачи, дороже |

Поменять можно через переменную `DEEPSEEK_MODEL` в `.env`.


## Про безопасность ключа

Ключ лежит только в `.env`, который добавлен в `.gitignore`. В репозиторий коммитится `.env.example` с пустым значением. Если ключ случайно попал в коммит — его нужно отозвать в панели DeepSeek и выпустить новый: переписывание истории git не помогает, публичные репозитории сканируются ботами в реальном времени.
